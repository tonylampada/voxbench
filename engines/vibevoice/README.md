# VibeVoice-Realtime-0.5B engine

Wraps [`microsoft/VibeVoice-Realtime-0.5B`](https://huggingface.co/microsoft/VibeVoice-Realtime-0.5B)
(MIT, 0.5B Qwen2.5 backbone + a 7.5 Hz acoustic tokenizer and a 4-layer diffusion head)
behind the v2 contract. 24 kHz mono out, 25 built-in preset voices in 10 languages,
native PCM streaming.

It is the **quickest streamer in the fleet** — first PCM byte at 40 ms, tied with
VoxCPM2, and unlike VoxCPM2 it is also fast to finish (4.5× realtime against 2.7×).

## Where this came from, and why that needs saying

Microsoft published VibeVoice in August 2025, then **unpublished it in September 2025**
after "instances where the tool was used in ways inconsistent with the stated intent".
For a while the code existed only in community forks. That is no longer the situation,
and everything here comes from Microsoft's own accounts:

| Thing | Source | State when this engine was built (2026-08-14) |
|---|---|---|
| Weights | `microsoft/VibeVoice-Realtime-0.5B` on Hugging Face | public, ungated, MIT, 629k downloads, created 2025-12-04 |
| Code | `github.com/microsoft/VibeVoice`, pinned to `94da20d98b2fa7688e9cbfaf7692ddb4954f7600` | public, MIT, 52k stars, last push 2026-07-24 |
| Preset voices | `demo/voices/streaming_model/*.pt` in the same checkout | 25 `.pt` files, ship with the code |

No mirror, no re-upload, no anonymous fork. Two things a future reader should still know:

- `vibevoice/modular/modeling_vibevoice.py` in the restored repo opens with
  `# copied from https://github.com/vibevoice-community/VibeVoice/...` — Microsoft
  restored part of its own repo *from* the community fork. The lineage is public but it
  is not an unbroken first-party line.
- The model card claims every output carries "an audible disclaimer (e.g. 'This segment
  was generated by AI')" and "an imperceptible watermark". **Neither is in the released
  code** — grep for `watermark` or `disclaimer` and the only hit is a licence comment in
  the DPM-solver file. Unlike chatterbox-ptbr, which really does embed a Perth watermark,
  what comes out of here is unmarked audio. Do not repeat the card's claim as fact.

Inference code was read before it was run: nothing in `vibevoice/` opens a socket, phones
home, or writes outside a `save_pretrained` target. The one `subprocess` use is ffmpeg
decoding in `processor/audio_utils.py`, on the ASR path this engine never touches.

## Build (from the repo root — the image bakes in `voices/`)

```
docker build -f engines/vibevoice/Dockerfile -t tts-vibevoice:gpu .
```

## Run

```
../tts up vibevoice        # port 8895
```

Weights come from the mounted HF cache (~1.6 GB); first run downloads them. Startup after
that is **10 seconds** — no torch.compile, no warmup pass.

## It cannot clone, and that is deliberate upstream

Microsoft removed the acoustic **encoder** from the public checkpoint ("Removed acoustic
tokenizer to avoid users creating embedding on their own"). Loading the model prints a
wall of `acoustic_tokenizer.encoder.* newly initialized` warnings — those random weights
are never used, the decode path only needs the decoder. The consequence is that there is
no way to turn a reference clip into a voice: a preset is a **prefilled KV cache** of the
model reading a reference, not an embedding anything here can compute.

So the engine behaves like kokoro and piper: `/v1/voices` lists the whole shared library,
and every reference id comes back 400 with that explanation. Its own 25 presets are
`kind: "builtin"`.

Ids are the vendor's filenames, verbatim (`pt-Spk1_man`, `en-Carter_man`) so a voice can
be traced back to the upstream file. Language comes from the filename prefix, which is not
always ISO 639-1 — `jp`→`ja`, `kr`→`ko`, `sp`→`es`, and `in-Samuel_man` is Indian-accented
**English**, mapped to `en`.

Per language: en 7 presets, de/fr/it/ja/ko/nl/pl/pt/es 2 each.

## Knobs

| Param | Range | Default | Notes |
|---|---|---|---|
| `cfg_scale` | 1.0–3.0 | 1.5 | vendor default; above ~2 the voice gets tense |
| `inference_steps` | 1–50 | 5 | vendor default is 5; DDPM steps per acoustic latent |
| `seed` | 0–2³¹−1 | 42 | see below |

`seed` is spent on torch's global RNG immediately before the decode, because VibeVoice
takes neither a seed nor a generator: the diffusion head draws its initial noise with a
bare `torch.randn` and `dpm_solver` calls `randn_tensor(generator=None)`, so the global
generator *is* the sampler's RNG. Safe because `gen_lock` already serializes generation.
Defaulted by the server, not left to the model — unseeded means a different take per
request, which is the drift we already paid for once on voxcpm2. Verified: same text +
same knobs + seed 42 twice → byte-identical WAV; seed 7 → a different one.

## Contract mapping

- One decode per request. **No text chunking** — the model does long form natively
  (8 k context ≈ 10 minutes of audio) and windows the text itself, so unlike voxcpm2
  there is no `MAX_CHUNK_CHARS` and no seam between pieces. A 42 s paragraph is one take.
- Streaming is the model's own `AudioStreamer`, and an abandoned stream is genuinely
  **stopped**: `generate()` polls `stop_check_fn` between steps, so a client that hangs
  up frees the GPU within a step instead of after the whole utterance (which is what
  voxcpm2 costs). `bench/abort-latency.py vibevoice`: **0.19 s** to first audio on the
  request right after an abort, against 0.17 s idle — the abandoned utterance is not
  waited out at all.
- `attn_implementation="sdpa"`. The vendor tested `flash_attention_2` and warns SDPA
  "may result in lower audio quality"; flash-attn has no wheel for this base image and
  building it is minutes of compile for an engine we are still evaluating.
- Voice presets are pickles, and torch **cannot** load these with `weights_only=True`:
  they hold `BaseModelOutputWithPast`, and torch's safe unpickler accepts only exactly
  `dict`/`OrderedDict`/`Counter` as a SETITEMS target — subclasses included in the
  refusal. So `server.py` scans each file's pickle opcodes and refuses any that names a
  global outside `SAFE_GLOBALS` before handing it to `torch.load`. All 25 shipped presets
  name five: `OrderedDict`, `BFloat16Storage`, `_rebuild_tensor_v2`, `DynamicCache`,
  `BaseModelOutputWithPast`. `test_preset_guard.py` is the regression guard.

## Measured

`bench/results/vibevoice.json`, bake-off sentences, RTX 4090.

| | en short | en long | pt short | pt long |
|---|---|---|---|---|
| realtime | 4.66× | 4.52× | 4.28× | 4.62× |
| stream TTFB | 40 ms | | 40 ms | |

VRAM **3214 MiB** for the server process. RAM 598 MiB idle → 1311 MiB peak.

Caveat on `vram_idle_mib`/`vram_busy_mib` in that JSON (14736/14942): this engine was
measured **alongside** the resident voxcpm2 and whisper services rather than alone, so
those whole-card figures are not comparable with the other engines' rows. The per-process
`vram_apps` number is the one to read.

## How it reads, in both languages

`samples/` has the same text through this engine and through voxcpm2, side by side —
short, long, and a real paragraph. Word error rate is whisper large-v3-turbo
transcribing the output back against the input text (lower is better; it scores the
engine's diction, not its charm):

| | vibevoice | voxcpm2 |
|---|---|---|
| **en** short / long / paragraph | 0.000 / 0.000 / 0.064 | 0.000 / 0.000 / 0.080 |
| **pt** short / long / paragraph | **0.538** / 0.062 / 0.130 | 0.077 / 0.016 / 0.016 |

English is a wash — both are clean, and VibeVoice is nearly twice as fast getting there.

Portuguese has one specific, repeatable failure: **the opening clause of a short
utterance comes out as mush, and the rest is fine.** "Capitão, o deploy passou" is
transcribed "Capitão Falando em Toy, passou", and then the model recovers and reads the
remaining twelve words at roughly voxcpm2's quality. Give it three words of runway and
the problem disappears entirely — prefixing "Bom dia. " to that exact sentence yields
"Bom dia, Capitão. O deploy passou. Dois pull requests mergeados, um esperando a sua
revisão", correct down to the anglicisms (`samples/vibevoice-pt-short-leadin.wav`).

So this is a cold-start problem, not an inability to speak the language: the model's own
card warns that very short inputs destabilise it, and non-English inputs evidently need
more runway than English ones. On a paragraph it holds together for 42 s in one take with
no seams, which is what it is sold on — it just costs 0.13 WER against voxcpm2's 0.016,
mostly in the first sentence.

Portuguese here is also a **vendor-experimental** feature by their own words: the model
is trained on English, and the nine extra languages ship "for users to explore and share
feedback", untested by Microsoft. It is pt, not pt-BR, and the accent is European-ish.

## Warts

- **Short Portuguese utterances are unreliable** (above). If you drive this from the
  board, give it a lead-in or use it for longer messages.
- `bench/conform.py vibevoice` reports **one violation**, `speech reference
  (kokoro-af-alloy-en)`. The harness picks a reference clip whose `origin` is the engine
  and falls back to *any* reference when there is none, then demands a 200. There is no
  vibevoice-origin clip in `voices/library/` because `bench/mkvoicelib.py` has not
  rendered this engine's builtins yet — doing that needs a `plan_vibevoice` there plus
  seed sentences for `ko` and `pl`, which `SEED` is missing. Refusing a foreign
  reference is the contract's clause 5, so the engine is right and the check is
  over-strict for a non-cloning engine with an empty own-origin set.
- Research licence in spirit: MIT weights and code, but the card says "limited to
  research purpose use" and "we do not recommend using VibeVoice in commercial or
  real-world applications". The MIT grant and that sentence are not the same instrument;
  someone should decide which one governs before this ships in anything.
- `transformers` pinned to `4.51.3` — the model's own `[streamingtts]` extra pins it, and
  the streaming code reaches into `DynamicCache` internals that moved later.
- Loading logs a tokenizer-class mismatch warning (`Qwen2Tokenizer` vs
  `VibeVoiceTextTokenizerFast`) and the encoder-not-initialized wall. Both are upstream's
  own loading path.
- Larger siblings exist (`VibeVoice-1.5B`, 64 k context; `VibeVoice-Large`, gated).
  Not tried: the 0.5B is the one that fits beside the resident services, and its
  Portuguese problem is a conditioning issue that a bigger model may or may not fix.
